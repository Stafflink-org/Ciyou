# Internationalisation (français, anglais, arabe)

Le client a validé trois langues : **français (langue de référence et de repli)**, **anglais**, **arabe (écriture de droite à gauche)**. Ce document donne la convention pour traduire le reste de l'application module par module.

## Ce qui existe

| Élément | Emplacement |
| --- | --- |
| Moteur de traduction (sans dépendance, API proche d'i18next) | `packages/web/src/i18n/core.ts` |
| Fournisseur de langue, hooks `useTranslation` / `useLocale` | `packages/web/src/i18n/I18nProvider.tsx` |
| Liaison shell (textes du kit, menu de langue, sélecteur compact) | `packages/web/src/i18n/shell.tsx` |
| Socle commun (namespace `common` : actions, jours, shell, erreurs, connexion, statuts) | `packages/web/src/i18n/{fr,en,ar}/common.json` |
| Traductions propres à une application (nav, auth, accueil…) | `apps/<app>/src/i18n/{fr,en,ar}/<namespace>.json`, enregistrées dans `apps/<app>/src/i18n/index.ts` |
| Libellés d'énumérations (statuts, rôles, modes…) | français : `packages/shared/src/constants/labels.ts` ; en/ar : `labels-i18n.ts` |

## Choix de la langue

Priorité : préférence enregistrée sur le profil (`users/{uid}.locale`), puis choix mémorisé sur l'appareil (`localStorage`, clé `golink:locale`), puis langue du navigateur, puis français. Le changement de langue depuis le menu utilisateur (ou le sélecteur FR / EN / AR des pages d'accès) s'applique immédiatement et s'écrit sur le profil. Le fournisseur pose `lang` et `dir` (`rtl` pour l'arabe) sur `<html>`.

Les chiffres restent latins en arabe (`ar-u-nu-latn`, usage des marchés DZ, MA, TN). Utiliser `intlLocale()` pour `Intl.*` et `toLocaleString`.

## Écrire une traduction

1. Créer (ou compléter) `apps/<app>/src/i18n/fr/<module>.json`, puis les fichiers `en` et `ar` avec **exactement les mêmes clés**. Un fichier par module et par langue = un namespace du nom du module (`commandes`, `livreurs`…).
2. Enregistrer les trois fichiers dans `apps/<app>/src/i18n/index.ts` avec `addResources('fr' | 'en' | 'ar', '<module>', arbre)`.
3. Dans le composant :

```tsx
const { t, label, locale } = useTranslation('commandes');
t('titre');                       // namespace par défaut du hook
t('common:actions.save');         // autre namespace
t('resume', { count: 3, name }); // variables {{name}} et pluriels resume_one / resume_other
label('ORDER_STATUS_LABELS', order.status); // libellé d'énumération
```

Règles :

- Clés en anglais camelCase, regroupées par écran (`header.title`, `table.columns.status`). Jamais de phrase comme clé.
- Pluriels : suffixes `_one` / `_other` (l'arabe utilise en plus `_zero`, `_two`, `_few`, `_many` si nécessaire, selon `Intl.PluralRules`).
- Jamais de concaténation de fragments : une phrase entière avec variables `{{...}}` (l'ordre des mots change en arabe).
- Repli garanti : clé absente dans une langue, affichage du français ; absente partout, affichage de la clé. Un écran n'est donc jamais cassé, on peut traduire progressivement.
- Ne pas traduire : marque Ciyou Eats, codes, identifiants, adresses e-mail, montants (formatés par `Intl`).
- Hors composant React (fonctions utilitaires) : `translate('module:cle', vars)` et `getLocale()` ; le composant appelant doit lui-même être abonné à la langue (`useTranslation`) pour se rafraîchir.
- Ne pas mettre de traduction dans un `useMemo` sans y mettre `locale` en dépendance (colonnes de tableau, options de filtre).

## Énumérations (labels.ts)

`labels.ts` reste la source française. Pour ajouter une langue à une table, compléter la table correspondante dans `labels-i18n.ts` (même clés). Lire ensuite avec `labelOf(table, cle, locale)` ou `label(table, cle)` du hook. Ne plus lire directement `ORDER_STATUS_LABELS[...]` dans les écrans traduits.

## Écritures de droite à gauche (RTL)

Le kit `@golink/ui` est entièrement en propriétés logiques. À respecter dans tout nouveau code :

- `ms-*` / `me-*` / `ps-*` / `pe-*` à la place de `ml-` / `mr-` / `pl-` / `pr-` ; `start-*` / `end-*` à la place de `left-` / `right-` ; `text-start` / `text-end` ; `rounded-s-*` / `rounded-e-*` ; `border-s` / `border-e`.
- Icônes directionnelles (chevrons, flèches précédent / suivant, retour) : ajouter `rtl:-scale-x-100`. Les icônes non directionnelles (recherche, cloche, coche) ne se retournent pas.
- Centrage absolu (`left-1/2 -translate-x-1/2`) : inchangé, symétrique.
- Valeurs à lecture toujours gauche-droite (e-mail, numéros, code) : `dir="ltr"` sur l'élément, ou `dir="auto"` pour un contenu saisi par l'utilisateur.
- Les animations de panneaux latéraux suivent `--gl-dir` (1 en LTR, -1 en RTL), posé par la feuille de style du kit selon `html[dir]`.

## État de la traduction (au 26/09/2026)

Traduit en fr / en / ar : shell (barre latérale, barre haute, notifications, menu utilisateur, sélecteur de langue), navigation des deux applications, accueil des deux applications, écrans de connexion, mot de passe oublié, définition du mot de passe, accès refusé, page introuvable, erreurs de route, messages d'erreur Firebase, statuts de commande (fiche commande, liste, chronologie, ticket, fiche client, livreurs).

À traduire module par module (les textes restent en français tant que non traités, sans casse) : pages de chaque rubrique (`features/*`), écran d'authentification à deux facteurs de l'admin, garde d'accès du restaurant, exports CSV / Excel, e-mails et notifications envoyés par les fonctions cloud. Ordre conseillé : commandes, produits, livreurs, finances, puis les rubriques secondaires.

## Traduction automatique (Azure Translator)

Les fichiers `fr/*.json` restent la source écrite à la main. Pour ne pas traduire `en`/`ar` clé par clé, une traduction automatique (Azure Translator, même principe que StaffLink) peut compléter les clés manquantes.

### Obtenir la clé Azure (le client la fournit lui-même)

1. Sur [portal.azure.com](https://portal.azure.com), créer une ressource **Traducteur** (Translator) : Créer une ressource → rechercher « Translator » → région (ex. `francecentral`), niveau tarifaire selon le volume attendu (F0 gratuit pour démarrer, ~2 millions de caractères/mois).
2. Une fois créée, ouvrir la ressource → **Clés et point de terminaison** : copier une des deux clés (« Clé 1 » ou « Clé 2 ») et la **région**. Le point de terminaison par défaut (`https://api.cognitive.microsofttranslator.com`) convient à la quasi-totalité des ressources ; ne le changer que si le portail Azure en indique un autre pour la ressource.
3. Dans le super admin Ciyou Eats : **Plateforme & sécurité → Traduction**, coller la clé et la région, cocher les langues actives (fr est toujours la langue source), régler un plafond mensuel de caractères pour maîtriser le coût, cliquer **Tester la connexion** puis **Enregistrer**.
4. La clé n'est jamais rechargée dans le formulaire par la suite : le champ reste vide (« conservée ») et seuls les 4 derniers caractères sont affichés pour vérification.

### Utilisation dans le produit

- **Fiches produits, sections, pages d'information, articles d'aide, gabarits de messages** : bouton « Traduire automatiquement » dans l'éditeur concerné du back-office (restaurant ou super admin), qui appelle `translateTexts` et remplit les champs `en`/`ar` (modifiables ensuite à la main). Les traductions manuelles ne sont jamais écrasées par un nouvel appel.
- **Interface (fichiers `apps/*/src/i18n/{en,ar}/*.json`)** : `npm run i18n:translate` (mode aperçu par défaut) puis `npm run i18n:translate --apply` pour écrire. Le script ne remplit que les clés **absentes** du fichier cible — une clé déjà présente (même identique au français) est considérée comme déjà relue et n'est jamais retouchée.
- Le cache serveur (`translations`, clé = hash du texte + langues) évite de payer deux fois la même traduction ; un plafond mensuel de caractères (réglable dans le super admin) protège du dépassement de coût.
- Si la traduction automatique n'est pas configurée, désactivée, ou qu'Azure répond une erreur : `translateTexts` renvoie une erreur claire et l'appelant conserve toujours le texte d'origine (jamais d'écran cassé).
