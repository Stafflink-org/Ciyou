## Incident et correctif — clé API Firebase, développement local bloqué (29/09/2026)

**Bug trouvé par la tâche `client-lot2-parcours-achat`, causé par un correctif de sécurité antérieur.** Après une alerte GitGuardian (clé Firebase publique détectée sur GitHub — normal par conception, mais sans restriction de domaine), une restriction de référent HTTP (`http://localhost:*/*`) avait été ajoutée à la clé web Firebase (`37bfbf9b-…`, celle utilisée dans `apps/*/src/lib/firebase.ts`).

**Conséquence non détectée pendant ~2h30** : Google Cloud ne supporte pas les jokers sur le numéro de port dans les restrictions de référent HTTP (seulement en début ou fin d'URL, jamais au milieu) — la restriction posée bloquait donc silencieusement **tout accès Auth/Firestore/Storage depuis n'importe quel serveur de développement local**, quel que soit le port (5173-5199, 8081, 19006, 3000…), sur les trois apps (admin, restaurant, client). Vérifié et reproduit avec `curl` direct sur `identitytoolkit.googleapis.com`.

**Correctif** : restriction de référent retirée (`browserKeyRestrictions: {}`), la clé reste restreinte aux seuls services Firebase (`apiTargets`, inchangé) — c'est cette restriction-là qui contient réellement le risque, pas le référent. La vraie protection des données reste les règles de sécurité Firestore/Storage (authentification + autorisation par requête), pas le secret de cette clé, qui est publique par conception dans tout site Firebase. Revérifié en direct : connexion et inscription fonctionnent à nouveau sur localhost.

**Reste à faire, si une restriction de domaine est vraiment souhaitée** : lister explicitement chaque port utilisé (fragile, les ports de dev changent d'une tâche à l'autre) ou mettre en place App Check, la protection recommandée par Google pour ce cas précis (jeton d'attestation par appareil/app, indépendant du référent).

## Correctif critique — encaissement Stripe manquant en acceptation automatique — 28/09/2026 (tâche `stripe-autoaccept-fix`)

**Bug réel corrigé (argent réel non encaissé)** : quand un commerce a le réglage « acceptation automatique » activé (`restaurants/{id}/settings/orders.autoAccept`), la commande passait directement au statut `preparing` sans que le paiement Stripe (`PaymentIntent`, `capture_method: manual`) ne soit jamais capturé/encaissé. Le montant restait seulement **autorisé** (bloqué sur la carte du client, jamais débité) — alors même que la commande était acceptée et livrée. Le chemin d'acceptation **manuelle** par le restaurant (`transitions.ts::acceptOrder`) encaissait correctement via `capturePayment` avant la transition de statut ; cette étape n'avait jamais été répliquée dans la branche `autoAccept` de `placeOrder` (`functions/src/orders/place.ts`), qui écrivait `status: 'preparing'` en gardant `payment.status` à la valeur brute de l'autorisation (`'authorized'`, jamais `'paid'`).

**Correctif** (`functions/src/orders/payment.ts`, `functions/src/orders/place.ts`) : factorisation de l'appel Stripe de capture (`captureIntentRaw`) et nouvelle fonction `captureAuthorizedIntent` (sans écriture Firestore, car le document `payments` n'existe pas encore à ce stade de `placeOrder` — l'identifiant de commande n'est attribué que dans la transaction qui suit). `placeOrder` appelle désormais cette capture immédiatement après l'autorisation Stripe, si `autoAccept` est réglé et que l'autorisation a réussi, **avant** l'écriture transactionnelle de la commande. Si la capture échoue (ex. incident Stripe), l'auto-acceptation est désactivée pour cette commande précise : elle est créée normalement au statut `new` (autorisation intacte), à charge du restaurant de l'accepter manuellement — ce qui retente l'encaissement via le chemin manuel déjà correct, avec sa gestion d'échec existante (paiement refusé → commande annulée automatiquement, client prévenu). Aucune commande n'est donc jamais acceptée (auto ou manuelle) sans encaissement réel réussi.

**Autres points d'entrée vérifiés (pas de régression)** : les commandes programmées (`scheduledFor`) forcent `autoAccept = false` dans `placeOrder`, et la tâche planifiée `releaseScheduled` (`functions/src/orders/scheduled.ts`) les fait toujours repasser par le statut `new` (jamais directement `preparing`), donc elles empruntent systématiquement le chemin d'acceptation manuelle correct. Aucun autre point de création de commande (import, simulation) n'existe dans `functions/src` — `placeOrder` est l'unique créateur de commandes.

**Tests réels sur `golink-9f16d`** (`node scripts/tests/stripe-autoaccept-fix.flow.mjs`, décor isolé `saf-*` nettoyé en fin d'exécution) — **13/13 OK** :

- Non-régression du chemin manuel (`autoAccept: false` sur le même commerce) : commande `new` → `acceptOrder` → `payment.status = 'paid'`, PaymentIntent Stripe `succeeded` confirmé côté API — inchangé par le correctif.
